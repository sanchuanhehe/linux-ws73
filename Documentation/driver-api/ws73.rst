WS73U / WS73E Wi-Fi / BLE development baseline
=============================================

Status and scope
----------------

This branch is a development series based on Linux
70dd4ee72eb2d5793c62e71c14e3aba78e5a4e56. The wire codecs are executable
kernel code consumed by the native HCI adapter and KUnit tests. The shared module also contains
firmware validation, bounded download execution and a one-shot entry joining
fresh HCC identity to original-file acquisition and board preparation.
The USB parent can issue fixed boot READM then VERSION observations, or
serialized runtime HCC identity/version queries with independent RX, and drain its
requests on disconnect. It does not select/download firmware,
register hci_dev or auxiliary consumers, or provide functional BLE/Wi-Fi.
Production code never generates controller completions. An explicit KUnit-only
controller model now replies to two setup commands through the native HCI stack;
its synthetic replies are not physical evidence. A separate userspace
FunctionFS peer now completes native HCI initialization through the shared
USB owner and auxiliary endpoint, including standard management-channel
identity checks and acknowledged automatic close. No hardware or SparkLink
qualification is inherited.

A failed boot observation now enters the same parent terminal/fault-work path
as a runtime failure: admission closes, outstanding transfers are cancelled,
and disconnect joins both initialization and fault work. No retry is scheduled.
The hardware-free USB tools exercise the fixed READM on synthetic two-endpoint
devices, including legitimate zero, invalid lengths, timeout and removal.
They cannot establish cold-chip register accessibility on real U/E hardware.

Runtime USB wire helpers now encode a single HCC record and queue-control
descriptors and validate bounded receive aggregates for BLE (queue 7) and
platform messages (queue 9), plus function notifications (queue 10) on RX
and explicit no-flash customization records on TX.
They are exercised with synthetic inputs;
the runtime USB path now consumes these helpers. The new runtime path has
not been exercised on physical hardware; it does not establish firmware
compatibility, version or boot/runtime identity agreement.

Native auxiliary BLE consumer (publication still gated)
-------------------------------------------------------

``ble.c`` owns one auxiliary endpoint per published BLE function, with exported
WS73-namespaced operations and per-device callbacks. Backend calls are sleepable
and serialized; RX/fault callbacks are serialized under an IRQ-safe lock and
must not sleep or reenter the shared interface. Unbind drains callbacks. Stop
gates RX before issuing a real backend disable; success must come from the
backend's action acknowledgement. First errors persist, with no reset API.
A BLE-local fault does not reset an active sibling. The physical owner remains
responsible for classifying and broadcasting whole-chip faults.

The owner must establish verified U/E USB identity, firmware epoch/version,
board/address inputs and startup handshakes, then disable/drain the initial BLE
session before publishing. These are constructor preconditions, not facts that
an arbitrary caller can prove by passing a boolean. The current USB observer
**does not call the publication operation**. Explicit KUnit and dummy_hcd test backends publish endpoints; they do not
supply hardware qualification.

The owner must abort IO and join RX/fault producers before removal. Removal
closes admission, joins active backend calls, clears backend pointers and
unregisters the auxiliary device. Its allocation, ID and core module reference
survive until the final device reference is released. Calls through a retained
reference return the terminal error without touching the removed backend.

``drivers/bluetooth/btws73.c`` is the actual auxiliary consumer. It allocates a
per-device ``hci_dev``, sets HCI_USB and the auxiliary parent, and implements
setup/open/close/flush/send. Setup requests real Local Supported Features and
BD_ADDR through the native HCI command engine. It requires LE-only features
and a nonzero/non-FF public address; no fixed address, invented capabilities,
SCO/ISO support or speculative quirk is supplied. Both queries now complete
against the explicit KUnit controller model. That model withholds the subsequent
Reset reply, so it does not qualify full HCI initialization or a physical controller.

TX accepts command/ACL packets only. It validates a copied H4 packet before
admission and limits the queue plus the active worker packet to 64 packets and
65536 H4 bytes. On success the adapter consumes the caller's skb; on error the
caller retains it. One worker encodes HCC into bounded storage and submits a
borrowed record to the shared backend. Local TX completion is not HCI command
success or controller credit. HCI command/data credits remain in the native
stack. Native ACL scheduling does not recover credits on a driver send error,
so any rejection during an active session latches a terminal error and withdraws
HCI. Flush stops TX admission and joins the worker. Purging accepted queued
packets during an active session is terminal too; an empty flush preserves RX.
Close separately stops receive admission and requests BLE disable.

RX uses the bounded H4 reassembler and copies complete event/ACL packets into
owned skbs before ``hci_recv_frame``. No borrowed URB storage escapes. Transport
or parse failure schedules HCI withdrawal in a separate worker; no fabricated
Command Complete or Hardware Error event is sent. Withdrawal cancels pending
native synchronous commands before unregistering HCI. Removal preserves any
existing local error in the shared endpoint, unbinds callbacks, drains TX and
fault work, unregisters HCI and releases its state. The explicit model verifies
ACL TX, fragmented event/ACL RX ownership, packet/byte quotas and invalid ACL
rejection. An active flush waiting for TX still admits RX, then becomes terminal
when purging accepted queued data. RX parse/allocation failures close TX admission
under the same lock before deferred withdrawal. Task-scoped FAILSLAB tests cover
the first allocation in TX/RX, including error retention and caller ownership.
ACL is checked at the HCI receive queue; HCI_INIT drops it before L2CAP. Full HCI
initialization, connection traffic and physical enable/disable remain unqualified.

The codec is built once as a hidden shared component, with its own BTWS73
namespace, avoiding duplicate definitions when both the consumer and codec
KUnit tests are enabled. BT_WS73 depends on WS73_USB, constraining built-in/
module combinations. The shared core selects auxiliary bus but not Bluetooth
or mac80211. Build and VM commands are in ``tools/testing/ws73/README``.

Runtime BLE backend and gated publication
----------------------------------------

``ble-link.c`` connects auxiliary enable/disable to the actual BLE action engine
and command/ACL records to the shared USB TX sequencer. Each call uses an absolute
2000-ms deadline with saturating arithmetic; success still requires exact local
transfer length and, for actions, a matching device reply. An action failure
faults BLE locally. A TX sequencing/transport failure also calls the physical
owner's fault handler because the shared TX object is terminal.

The USB parent owns this adapter, routes validated queue-7 records to it and
routes post-startup BLE notifications to its action engine. RX removes only the
four-byte HCC header and padding; H4 validation/reassembly remains in Bluetooth.
The receive/fault routing lock pins the child during callbacks. No sleeping
operation is performed under that lock. Shared fault closes the adapter; removal
aborts waiters, drains USB and initialization producers, detaches child routing,
then removes the endpoint and joins its backend calls before freeing the parent.

Publication checks startup DONE and acknowledged BLE DISABLED state, with no
retry after an adapter fault. The owner must separately establish identity,
firmware/board/address validity and drain old device data. These state checks
cannot prove a cold epoch or a hardware drain. A two-phase auxiliary allocation
installs routing before device registration can synchronously probe a consumer.
If that probe faults the adapter, publication removes the registered child and
returns the retained error. Registration does not imply HCI initialization.

The physical observer still never invokes publication, startup arm/run or the
loader. The adapter's action/data operations execute in injected-I/O KUnit,
including a synchronous auxiliary probe. A further explicit model now composes
this backend with the actual native HCI consumer: startup/customization,
acknowledged disable, publication and native open precede two setup queries and
ACL TX. Exact USB queue-control/data framing is checked independently, while
synthetic action and HCI replies traverse the aggregate decoder and RX routing.
Coalesced event/ACL data split across HCC records retains skb ownership after
source overwrite. Short action and data transfers exercise different fault
scopes; parent abort drains an in-flight command and prevents queued ACL TX.

That model still withholds Reset completion. It does not qualify full HCI
initialization, L2CAP, actual USB URBs or peer behavior; control tests check the
four-byte payload, not a submitted control setup packet. No firmware gate,
default address, board override or user ABI was added.

Runtime USB framing baseline
----------------------------

``drivers/misc/ws73/usb-wire.c`` follows the pinned SDK110
``hcc_usb_host_ops.c`` functions ``hcc_usb_xfer_write_data``,
``hcc_usb_xfer_write_desc`` and ``hcc_usb_tx_control_data``:

* Single data frames have type 0, a total-length field and a per-device
  sequence value, all little endian. A zero descriptor occupies the first
  64-byte slot; one already 8-byte-aligned HCC record follows, padded to at
  least 64 bytes. The first implementation caps the record at 4096 bytes.
* Control transfers have type 3, length field zero, sequence, and descriptor
  operation at offset 12. The actual USB transfer is 36 bytes. Queue switch
  (operation 1) carries a little-endian queue at offset 16; aggregation reset
  (operation 0) has no payload. Both operations must complete before using
  a newly selected queue. The sequence is not a reply transaction ID.
* Receive type 2 has a 92-byte prefix with at most 24 contiguous nonzero
  record lengths. Each record is bounded to 4096 bytes, must match the full
  outer queue value, and is checked before any view is published. BLE lengths
  exclude HCC; platform lengths include it. Queue-10 RX lengths exclude
  HCC, unlike the SDK Host customization TX allocation length. Unknown queues/services, holes,
  trailing bytes, truncated records and inconsistent platform lengths fail.
* Input views remain borrowed and immutable; service consumers still validate
  platform reply identity or H4 streams. Encoding never conveys device credit,
  HCI command success or Wi-Fi acknowledgement. No new service is advertised.

The existing BLE aggregate decoder remains unchanged in this increment, so
its original regression cases can still compare behavior independently.

``usb-tx.c`` serializes switch/reset/data through one per-instance mutex and
one fixed 4160-byte buffer. Its injectable synchronous send operation must
return actual transfer length and abort on disconnect. All steps share an
absolute deadline, capped at 2000 ms per transfer. A short/oversized transfer,
transport error, cancellation or expired deadline makes the instance terminal;
clearing the external fault does not allow another submission. Queue state is
published only after both controls complete. Invalid input is rejected before
any I/O. The caller retains its immutable record throughout this synchronous
call; no skb is consumed. The owner must stop admission, cancel I/O and join
callers before releasing the instance. These are tested sequencing contracts,
not qualification of asynchronous USB teardown, firmware credit or runtime
communication.

Serialized runtime identity and version
--------------------------------------

``runtime.c`` serializes GET_CHIP_TYPE and GET_VERSION in one per-device
request object. A command mutex admits only one caller (-EBUSY otherwise);
each kind is permitted once per instance (-EALREADY on reuse), with no reset
API. The expected reply ID and completion are installed before TX. RX completes
through a separate entry point and never waits on the command mutex.
It publishes identity only after the local TX completes successfully and a
valid matching reply arrives within the deadline. Unrelated reply IDs do not
complete it; duplicate matching replies before consumption, malformed replies,
failed TX, timeout and removal enter a terminal error. RX never waits for the
sleeping query. Abort wakes its waiter and prevents further request transfers.
An expired request cannot accept a late reply or issue another query. Both
startup queries share one absolute deadline; starting the version stage does
not renew it. A late chip reply cannot satisfy the different version reply ID.

The USB parent distinguishes two- and five-endpoint interfaces and validates
bulk IN/OUT, interrupt IN and register OUT/IN roles for runtime. It starts one
bounded RX URB before the initialization worker sends the query. Runtime OUT
URBs use URB_ZERO_PACKET for maximum-packet boundary semantics. Completion
only validates/dispatches the bounded aggregate and requeues RX; fault work
performs blocking URB cancellation. Disconnect closes submission admission,
wakes the query, joins anchored and already-unanchored RX/TX callbacks, then
joins initialization/fault work before releasing buffers and the USB reference.
Interrupt RX is active as described below; register endpoints remain inactive.

Runtime identification remains an **observation**, including when the device
was started by another host. Without a verified firmware epoch, tokenless HCC
cannot distinguish a stale device-generated reply from a fresh reply with the
same ID. This implementation does not use such an observation to register a
function or bypass the boot/cold-start and firmware-version gates. Boot and
runtime objects do not share requests, callbacks or identity cache. Unknown
outer types/queues and unsupported notification tags/actions are dropped as
whole aggregates. Malformed known records terminate the observation.
The observation-only USB parent does not publish a BLE endpoint or forward
BLE frames to the native HCI consumer yet.

GET_VERSION is SDK110 platform request 13 with one input byte equal to 1,
padded to a 32-byte HCC record. Reply 7 contains status u32, returned length
u32 (=8), firmware u32 and ROM u32, all little endian. The platform payload
length is 16; the HCC length includes the header and must cover all 24 bytes.
Both raw version words are preserved. ``plat_misc.c`` defines firmware bytes
as a/b/c/d from most to least significant and ROM fields as v16/r8/c8; its
printed ROM "1.0.0" is a constant, not the reported word. Neither that string
nor a plausible version value proves the selected firmware image is running.
The parent logs observations only after both queries succeed, and names the
chip or version stage on failure.

Interrupt endpoint reception
----------------------------

SDK110 ``usb_dev_notification`` is eight bytes: a little-endian u32 event
bitmap followed by a little-endian u32 high-priority-pool field. The decoder
requires the exact actual transfer length and preserves raw words, including
zero and unknown bits. The pool field is not interpreted as a software send
quota or Bluetooth command credit. SDK flow-control/PM/BCPU acknowledgements
are not BLE enable replies; no function or PM state is derived from them here.

Runtime initialization starts an independent interrupt-IN URB before bulk RX
and the platform queries. Its own allocated DMA buffer is not shared with state
updated by other callbacks. The descriptor supplies the interrupt endpoint and
interval. A malformed notification or USB error enters the same terminal and
stop/drain path as bulk RX. DEVICE_PANIC (bit 6) and BCPU_PANIC (bit 18) take
precedence over BSP_READY and fail the device with -EIO. High-priority packet
loss (bit 5) conservatively fails with -ENOBUFS because a missing control reply
cannot establish successful initialization. No automatic recovery is inferred.

BSP_READY (bit 0) is recorded once per object as an observation, including the
raw pool word. Duplicate/zero notifications and unrelated bits do not complete
queries or make functions available. A device fault after initialization still
closes admission and cancels both receive URBs. Disconnect explicitly joins
both URBs, including completions that already left their anchors, then joins
initialization and fault work before freeing either buffer. An optional dynamic
debug message marks that actual drain boundary for lifecycle verification.
Register endpoints, invoking BLE controls from validated initialization,
firmware readiness and publishing the native auxiliary/HCI consumer from this
USB owner remain pending.

Function notification reception
-------------------------------

``service.c`` decodes SDK110 service 5, subtype 0, queue 10. The first HCC
byte is **0x50**, because ``hcc_comm.h`` puts service in the high nibble;
``hcc_transfer_param`` has a different bitfield order and is not a wire header.
Notification RX length excludes HCC's four bytes. This differs from the Host
customization TX allocation-size convention; applying that convention to RX
would reject short valid replies and accept inconsistent lengths.

The four-byte little-endian tag contains type and body length. Known status
messages require exactly four declared body bytes, even when HCC includes
allocation padding. Device status type 2 accepts BOOT_FINISH=1 and
CUSTOMIZE_RECEIVED=2. Action status type 4 accepts BLE_OPEN=0 and BLE_CLOSE=1.
The decoder rejects invalid values, services, subtypes and lengths without
changing its output. Other tags and SLE actions 2/3 are unsupported; there is
no SLE consumer. Padding is never scanned for another notification.

The USB aggregate decoder validates all records before copying notifications
into its result. A malformed or unsupported final record cannot publish earlier
valid statuses. The USB parent currently records each of the four notification
kinds at most once per device object; this bounded observation is not a request
completion, persistent readiness state or a function registration. New USB
instances start with no observations. Queue-10 TX has a strict customization
encoder, but initialization does not send it without qualified inputs and
transaction sequencing. The BLE action engine and USB backend are described below;
initialization does not invoke them until their prerequisites are established.

BLE action transactions
-----------------------

``ble-control.c`` implements an independent per-device action state machine.
Its initial state is UNKNOWN, not DISABLED: a close before the first successful
open returns -EAGAIN. A command mutex admits one caller (-EBUSY otherwise).
After successful opposite actions, open/close can alternate; a redundant
request for the stable state returns -EALREADY without another transfer.
Before sending, the target, deadline and completion are armed under a spinlock.
The command is exactly LE32 25 (open) or 26 (close). Both actual four-byte TX and
one matching BLE action reply must succeed before the state is committed.

BOOT_FINISH and CUSTOMIZE_RECEIVED cannot complete this action waiter. RX can
complete independently while the sender sleeps. Wrong/duplicate action replies,
short/oversized/failed TX, expiry, cancellation and abort enter an immutable
failure state and wake the waiter. A valid reply cannot hide failed TX. A close
timeout never publishes DISABLED or permits another open. The first terminal
error is retained; there is no reset or blind retry. The common absolute deadline
covers send and wait and is capped to 2000 ms total without addition overflow.
An asynchronous caller must be aborted and joined before freeing its object.

The USB parent now routes validated action notifications to this state machine
and aborts it on shared device failure/disconnect. Before any action is armed,
notifications remain observations. A rejected action fails BLE locally without
resetting an active sibling or stopping shared RX; malformed shared wire input
and device-level faults retain their separate shared failure policy. No physical
coexistence guarantee is inferred from this distinction.

The prepared USB send backend accepts only messages 25/26. It builds request
0, class/interface OUT (0x21), value/index 0, wLength 4, with separate allocated
setup/data buffers. The driver already restricts binding to interface 0. The
control URB shares disconnect admission, anchoring, bounded waiting and explicit
completion joining with bulk transfers, and does not use bulk ZLP flags. Actual
transfer length remains distinct from action success. This backend is installed
in the per-device IO object. The physical observation worker does not call it.
The explicit dummy_hcd startup and HCI consumers now exercise it through
actual control URBs and independent action replies. There is no
user-triggerable physical bypass or new ABI; physical action qualification
remains open.

The caller still must establish firmware, board/customization and device epoch
before invoking an action, and independently check boot/address/HCI setup before
publishing readiness. Tokenless replies cannot authenticate an old epoch or an
old same-kind reply delayed across multiple successful action cycles. Ordered
one-reply-per-command device behavior remains a qualification assumption, not
something the synthetic repeated-action tests prove. The auxiliary/HCI consumer
and runtime adapter now implement caller lifetime/drain; physical publication
is still gated and no action caller is registered by USB initialization.

Customization encoding
----------------------

``customize.c`` encodes explicit host parameters for the SDK110 USB
``use_flash=0`` path. It writes fields individually in little endian, without
copying a native structure or installing vendor defaults. The record is
exactly 800 bytes: service/subtype 0x50, queue 10, HCC TX length 800 (including
HCC), tag type 0, tag length 140, then the customization body. The flash-use
word, flash-derived trim/address fields, structure padding and remaining
allocation padding are zero. This path does not override per-device addresses
or trims. Flash overrides remain unsupported.

Frequency/reference pairs place frequency in the high half-word. The first
six channel boundaries are packed in pairs, with the earlier boundary in the
high half-word; the seventh is a single value. Calibration count is limited
to 0..8, as documented by the SDK INI. The codec checks representation only;
it does not prove power, coexistence, regulatory or board suitability. Its
test vectors deliberately contain synthetic endian markers, not RF settings.

Queue-10 USB TX accepts only this exact record shape, including zero reserved
bytes, before any queue-switch/reset side effect. It uses the existing bounded
serial transport, with actual-length checking and terminal failure after a
short transfer. RX retains its separate device-notification decoder and length
convention. Encoding or USB TX success does not imply CUSTOMIZE_RECEIVED.
No initialization caller sends the new record yet; board profile selection and
subsequent boot/action gates remain pending.

The pinned SDK ``build/config/ws73_cfg_default.ini`` and
``hbsle_custom_fill_ini_param`` provide a more complete parameter source than
blindly copying ``CONFIG_NO_SUPPORT_INI`` defaults. In particular, the INI
contains eight calibration frequencies (6, 15, 26, 39, 60, 68, 72, 76), whereas
the no-INI default structure initializes the corresponding words to reference
20 without those frequency half-words. Neither path alone establishes board
compatibility for both U/E. No default board profile is selected here.

``customize-request.c`` adds a one-shot per-device transaction, with independent
RX completion and cancellation. Queue-switch/reset traffic occurs in PREPARING;
only immediately before the data submission does it arm WAITING. A premature,
duplicate or late CUSTOMIZE_RECEIVED is terminal. Unarmed observations do not
satisfy a future request. BOOT_FINISH and BLE action notifications cannot satisfy
this waiter. Exact USB transfer completion and one timely acknowledgement must
both succeed, within one absolute deadline capped to 2000 ms. Successful apply
cannot be repeated, and any failure retains its first error without retry.
Invalid parameters are rejected before consuming the transaction or doing I/O.

The USB parent initializes, routes notifications to and aborts this state on
shared failure/disconnect. Initialization still does not call apply: a known
firmware epoch and board-qualified parameters are prerequisites. Tokenless
status cannot authenticate the device epoch. As with BLE action state, an owner
adding a caller must join it before releasing the parent; the current parent
has no customization caller. Synthetic tests cover actual production transport
sequencing and an independent RX thread, not a physical customization exchange.

Board preparation and three-file execution
------------------------------------------

The USB parent's persistent boot IO object now includes the SDK's minimum
5-ms READY-to-payload delay. Its synchronous transport admits boot TX up to
32768 bytes, matching the executor's chunk limit, while boot RX remains capped
at 512 bytes. Runtime transfers keep their existing bounds. All memory is
allocated separately from borrowed inputs, and completion is joined before
freeing it; the larger TX capacity does not change submission/cancellation
ownership. No new user-triggerable entry point is added. The current parent
uses this object for fixed identity and boot-version observations. The shared private
``usb-io.c`` helper now owns synchronous URB allocation, submission, completion
join and READY sleep; its borrowed owner pointers stay live until all callers
are joined. The owner retains admission/error state and the anchor. Namespace
WS73_USB_IO and the hidden module preserve explicit module dependencies.

A separate ``WS73_USB_BOOT_TEST`` driver executes FILES/QUIT through these exact
helpers on dummy_hcd only, with synthetic ID ffff:3734. Its three synthetic
views have sizes 32769/32/32, exercising a full 32-KiB chunk plus the final byte
and two separate calibration-shaped inputs. FunctionFS independently verifies
commands, payload bytes, progress and no extra OUT after completion/failure.
Bad READY/FILES OK, timeout, removal at READY/payload admission, callback drain
and a new successful instance are covered at full and high speed. The test
checks both wire timing and the shared sleep call's own elapsed duration;
USB scheduling alone cannot prove that the required sleep occurred.

These are actual synthetic USB transfers, not original firmware execution.
Hash selection, identity, RAM/XO preparation and runtime re-enumeration are
not part of this fixture. Successful QUIT ends at WAIT_RUNTIME. The physical
parent still does not call the loader or bypass cold U/E and board gates.

Every USB deadline and BSP/function timestamp uses ``ws73_usb_now`` and its
boottime clock. The earlier BSP path used ``ktime_get`` instead; those domains
differ by suspended time and must not be mixed. This correction is not a
suspend/resume qualification or authorization to enable autosuspend.

``ws73_boot_load`` adds the fixed SDK110 USB preparation sequence before the
existing FILES/QUIT executor. It checks every image range and explicit XO trim
before the first write. Ten fixed RAM2/3/4 writes are followed by one XO write
at 0x40019408, packing coarse in the low byte and fine in the next byte.
Coarse 0..15 and fine 0..127 are admitted; no default trim is supplied. Each
``WRITEM 4 <address> <decimal-value> `` requires ``WRITEM OK`` before proceeding.
Only NUL response padding is allowed. Actual-length, cancellation and deadline
checks use the existing boot transport. A failed write/ack stops immediately;
it cannot continue with FILES or QUIT. The caller must discard a failed session,
not retry or restore guessed register values. Acknowledged preparation writes
are recorded separately from acknowledged image bytes.

The SDK ``plat_cali.c`` supplies the symbolic RAM sequence and values.
``plat_pm_board_ws73.c`` invokes RAM2/3 under ON_CHIP_LINUX_SDK, which the Linux
platform Makefile defines, and RAM4 under BT_EM_BUFFER_CALI_SUPPORT, enabled
in both inspected USB light configurations. ``hcc_usb_write_reg`` dispatches
boot writes to ``write_device_reg`` (decimal value and trailing space). The
firmware command table puts XO trim before the three files; the trim originates
from build configuration or INI, not from a universal device default.

The numeric RAM register addresses are cross-referenced to the pinned
``libws73-usb/src/ws73_usb_firmware.c`` preload sequence. This SDK checkout
references but does not contain the generated CLDO register-offset header;
no corresponding local platform object was found. Consequently that numeric
mapping is reference-implementation evidence, not independently verified vendor
register documentation or this project's U/E hardware qualification. The XO
address/width are explicit in the SDK ``plat_firmware.h``. This provenance and
board applicability remain gates for physical use; no register operation runs
in the USB observation driver yet.

The executor borrows already validated immutable image views. Full image/header
hash checks remain the firmware-request layer's prerequisite, as do live HCC
identity, cold-read qualification and board compatibility. Range checks alone
do not establish any of these. The injectable board transcript uses tiny synthetic
images and explicit non-production trim, checks all 35 send/receive operations,
and injects errors at every operation. Runtime XO temperature compensation,
device address provenance and native consumers remain separate pending work.

One-shot original firmware boot loader
--------------------------------------

``boot-loader.c:ws73_boot_start`` joins the existing components into one
serialized, sleepable attempt. A zero-initialized session records the current
phase, first error, fresh READM observation and transfer progress. Explicit
board trim is copied and range-checked before any IO. READM then selects exactly
one U/USB or E/USB profile; S/SDIO and E/UART are rejected. All three original
files must pass size, internal-header and complete-file hash checks before the
first RAM/XO write. There is no combined input or alternate-model retry.

The firmware bundle stays local to the call and holds immutable references
through preparation and every synchronous transfer. All return paths release
it, including partial acquisition. ``request_firmware_direct`` uses the kernel
firmware loader without a userspace fallback wait. Filesystem acquisition itself
is synchronous; USB cancellation does not interrupt a filesystem read. The
caller owns the device/IO/session until return. Cancellation and the unchanged
absolute deadline are checked again after input acquisition and before writes;
the underlying executor rechecks them around transfers. This is not a promise
of immediate teardown during a blocked filesystem operation.

Failures retain their original phase/error and cannot be retried with repaired
arguments. A successful second call returns -EALREADY without IO. Success means
WAIT_RUNTIME only; no firmware reference or cached boot state is transferred to
a new USB instance. The owner must independently qualify cold-register access
and board/trim applicability before calling this API. The physical USB observer
still does not call it, re-enumerate a device or publish BLE/Wi-Fi.

The dummy_hcd-only test additionally binds ffff:3735 for this whole path. It
obtains both original profiles through the actual firmware API in an isolated
VM, verifies all 11 preparation commands, strips only validated headers and
checks all transmitted bytes against local originals. Explicit fixture trim
1/2 is a model input, not a physical board default. The two USB speeds cover
U/E success, absent BTC, a changed code payload with recomputed header, mixed
U/E calibration, unsupported transports, removal during identity, bad first
WRITEM acknowledgement and fresh success. Every attempt calls start again to
verify terminal behavior. None of these transfers executes firmware on a chip
or qualifies cold access, register applicability or runtime identity agreement.

Startup handshake coordinator
-----------------------------

``startup.c`` sequences the actual customization and BLE action engines:
BSP_READY, customization TX/acknowledgement, BLE open TX/action, then BOOT_FINISH.
It holds independent BSP and BOOT completions. A one-shot arm operation captures
notifications before RX starts; the sleepable run follows identity/firmware and
board qualification. BOOT received after arm but before its wait is retained.
Unarmed notifications cannot satisfy a later session. Repeated BSP/BOOT are
idempotent status observations, unlike duplicate transaction acknowledgements.
An IRQ panic or high-priority loss overrides BSP in the same interrupt word.

The arm operation fixes an absolute deadline capped to 12000 ms; stages cannot
extend it. BSP waiting is additionally bounded to 6000 ms and BOOT waiting to
2000 ms; the two transaction engines retain their own 2000-ms limits. All clocks
share one monotonic millisecond domain. This is a bounded host policy, not a
measured device startup guarantee. The SDK board PM code waits 1000 ms then
5000 ms for BSP; its adjacent ``// 20000`` comment is not the executed value.
The status helper sleeps 10 ms and compares a millisecond timestamp against 2000.

The coordinator never holds its state spinlock across a transaction or callback.
Abort wakes both status waiters and aborts both transaction engines outside that
lock. Missing status, cancellation, transfer failure or contradiction prevents
later stages and retains a terminal failure. There is no automatic disable,
reset or retry after an uncertain startup. DONE means only these four handshakes
completed; address setup, HCI command completion and native consumer registration
are separate requirements. Tokenless notifications cannot establish firmware
epoch or board validity.

The USB parent owns this coordinator, routes validated notifications and aborts
it during shared failure/removal. Current observation-only initialization does

The following is protocol/call-chain evidence, not implemented BLE support.
The pinned ``driver/bsle/ble_driver/linux/ble_host_hcc.c`` and
``driver/platform/pm/plat_pm_wlan.c`` reveal distinct initialization stages:

#. ``ext_bluetooth_init`` calls ``pm_ble_open``; ``pm_svc_open`` performs the

#. ``pm_bsle_open`` registers service 5 and builds the customization message
   in ``driver/platform/cfg/customize_bsle.c``. It sends an 800-byte HCC buffer
   on queue 10, with subtype 0, tag type 0 and tag length equal to the actual
   customization structure, then waits for CUSTOMIZE_RECEIVED. These fields

   data; they are not a substitute for the separate BTC calibration file.

   value/index 0, four-byte message ID 25. ``ext_bluetooth_init`` subsequently

   address bytes before registering hci_dev. That helper returns local send
   status; it is not evidence of the controller's command completion.

   message 25 again; close sends 26. The upstream implementation must establish
   its own single function lifecycle and actual replies, not reproduce two
   untracked enables or the SDK's close-timeout success fallback.

``customize_bsle_ext.h`` defines the queue-10 tag as type u16, length u16.
Device-status tag type 2 carries a u32: BOOT_FINISH=1 or
CUSTOMIZE_RECEIVED=2. Action-status tag type 4 instead carries BLE_OPEN=0 or
BLE_CLOSE=1; the SDK translates OPEN=0 into callback boolean true. These
are different messages, and neither BSP/BCPU interrupt acknowledgement nor
USB transfer completion can replace them. SLE action values 2/3 are outside
this project's function support and do not justify an SLE adapter.

-------------------------------------

#. Obtain the per-device PM/bus context; power up and prepare patch loading.
   Reinitialize the bus. USB ``hcc_usb_reinit`` waits for the boot probe.
#. Apply calibration memory setup when enabled: RAM2/RAM3 under
   ``ON_CHIP_LINUX_SDK`` and BTC EM-buffer/RAM4 reuse under

   their applicability must be resolved before porting writes.
#. ``firmware_download_function`` serializes download and holds a wake lock.
   ``firmware_download/plat_firmware.c`` prepares the board CMU XO trim
   WRITEM, optional ROMBIN, code at 0x400000, Wi-Fi calibration at 0x430000,

BLE wire contract
-----------------

At the pinned SDK revision, the relevant files are:

* ``driver/platform/hcc/host/hcc_usb_host.h``: usb_package, RX message type 2,
  8-byte USB TX alignment (not the 32-byte alignment mentioned in generic
  HCC/SDIO comments).
* ``driver/platform/hcc/comm/hcc_bus_usb_comm.h`` and
  ``host/hcc_usb_host.c``: 92-byte RX aggregate header, 24 u16 record lengths,
  4096-byte per-record allocation limit, outer queue in usb_package.reserve.
* ``driver/platform/hcc/inc/hcc_comm.h``: four-byte HCC header; the stale
  five-byte comment is not its layout. Byte 0 has service in the high nibble
  and subtype in the low nibble; byte 1 is queue; bytes 2..3 are LE length.
* ``driver/platform/drv/device/romable/include/hcc_cfg_comm.h``:
  Bluetooth service 0 and queue 7; BSLE control service 5 and queue 10.
* ``driver/platform/hcc/comm/hcc.c``: BLE length excludes the four-byte HCC
  header, unlike some control messages. hcc_bt_tx_data uses bus alignment.
* ``driver/bsle/ble_driver/linux/ble_host_hcc.c``: H4 type prefix and a
  1500-byte transmit limit, pm_ble_enable/disable and asynchronous replies.
* ``driver/platform/pm/plat_pm_wlan.c`` and ``cfg/customize_bsle.c``:
  distinct BLE enable/disable requests and BSLE action-status replies.

``btws73_hcc_decode`` validates one complete RX aggregate before publishing
any fragment. It checks exact total length, message kind, full-width outer
queue, contiguous record-length entries, each record's service/subtype/queue
and payload bounds. At most 24 borrowed views are returned. Padding is not
interpreted as HCI data. Unknown outer types/queues return EOPNOTSUPP;
inconsistent inner identity returns EPROTO; bad bounds return EMSGSIZE.
Output is unchanged on every error. Input and output must not alias.

The decoder does not assume an HCC fragment is a complete HCI packet.
``btws73_hci_validate`` checks exactly one already-assembled H4 command/ACL
on TX or event/ACL on RX. SCO, ISO and direction-invalid types are rejected.
``btws73_hcc_encode`` validates before writing, emits a BLE HCC record with
zeroed 8-byte alignment padding, and leaves output untouched on failure.
It does not emit USB descriptors, switch queues or submit transfers.

``btws73_h4_feed`` now assembles event/ACL packets across validated fragments
in fixed 1500-byte storage. A call consumes at most one complete packet and
reports the consumed byte count, allowing coalesced packets without losing
their boundaries. Completed views borrow the stream storage until the next
feed/reset; the eventual HCI consumer must copy them before feeding again.
Invalid types and oversized lengths permanently fail that stream. Only an
explicit reset after stopping and draining the old producer may reopen it.
Partial headers and payloads are not dispatched. This implements assembly,
not an hci_dev, HCI command credit, or a real controller response.

The conservative 1500-byte fragment ceiling is an initial implementation
limit, not a measured RX firmware maximum. Fragmentation across aggregates,
USB short-transfer/reassembly semantics and actual BLE RX size distribution
still need a 110 capture. No speculative re-synchronization or success is
generated after malformed input.

Architecture decision 0001 (selected implementation)
---------------------------------------------------

HCI validation and H4 transmit framing stay local to drivers/bluetooth.
HCC receive and chip identity helpers now live in drivers/misc/ws73 and
are exported in the WS73 namespace. A per-device auxiliary BLE endpoint and
actual HCI consumer now exist; the USB owner does not publish that endpoint yet.
There is no Wi-Fi child or unused SLE interface. The USB owner currently provides bounded
boot observations, runtime HCC identity/version and notification reception,
and request teardown. Firmware loading and native consumers remain to be
integrated. Only actual Wi-Fi/BLE consumer needs justify extraction
into a shared directory. The selected shared-layer location is
``drivers/misc/ws73/``: USB ownership, chip identity, firmware, HCC routing
and device lifecycle belong there; BLE and Wi-Fi adapters remain in their
subsystems. This avoids making BLE-only builds depend on a Wi-Fi Host.
Use the auxiliary bus for actual Bluetooth/Wi-Fi children and namespaced
kernel symbols for their shared operations. The directory and cross-tree
arrangement still require maintainer review. Existing btrsi/RSI and the
auxiliary bus documentation inform the design; no parallel core is planned.

The codecs borrow caller buffers. The boot USB owner separately allocates
DMA-safe buffers and serial URBs in a per-device worker. Submission and
disconnect admission share a spinlock. Disconnect sets a terminal flag,
kills anchored URBs and joins initialization before releasing the parent;
each transfer joins its completion before freeing its request storage.
The worker does not retry failed reads or register functions. Runtime USB
queue sequencing and RX/IRQ callback drain are implemented. The new BLE
endpoint and HCI queue/stop contracts now have a runtime backend, but publication
still needs the qualified USB startup path. The native consumer has explicit synthetic positive data-path
checks; these are not USB integration or hardware qualification.
Protocol HCI credits remain separate from
USB queue slots. A BLE close must not reset an active Wi-Fi consumer.

  not establish a device-advertised credit or a wireless acknowledgement.
* ``WLAN_MSG_D2H_C_CFG_CFG80211_DATA_TX_STATUS`` dispatches to
  ``hmac_config_tx_complete_data``. Its ``dmac_tx_status_stru`` carries
  descriptor status, frame type, management/frame marker and user index;
  it contains no retry-count or final-rate field. The inspected handler checks
  descriptor success, handles the EAPOL key 4/4 marker and deferred PTK install,
  and has an ALWAYS_TX result path. A general ordinary-data per-MPDU completion
  contract is not established by this handler.
* Management status traverses ``hmac_mgmt_tx_event_status_etc`` and
  ``wal_cfg80211_mgmt_tx_status_etc`` to update a management waiter and its frame
  identifier. This does not qualify ordinary-data status either.

These are Host source call-chain findings at the pinned SDK revision. Device
producer behavior, exact USB wire layout and complete ordinary-data status
remain to be traced; the findings do not prove absence across all firmware.

A separate RX/security trace at the same pinned SDK gives concrete Host-side
metadata candidates:

* ``frw/frw_hmac.c:frw_hmac_rcv_netbuf`` removes the HCC header and calls
  ``frw_hmac_rcv_mgnt_data``. That path removes the FRW header, copies
  ``OAL_MAX_CB_LEN`` (32) bytes to the netbuf control block, then removes the
  control block and compacts the 36-byte reserved MAC-header area before
  setting the actual frame length. This is consumer evidence, not a traced
  device producer or a safe parser to copy without bounds checks.
* ``romable/frw_msg_rom.h`` declares a packed FRW extension with fields
  totaling eight bytes despite its ``4B`` comment. ``romable/oal_netbuf_common_rom.h``
  defines the 32-byte control and 36-byte MAC-header reservations. In
  ``device_common/dmac_ext_if_device_rom.h``, the RX control combines 20-byte
  info, four-byte status and eight-byte statistics declarations.
* The info declaration has channel number at byte 7 and a device virtual
  header address at bytes 16..19; that address must never become a Host
  pointer. Status declares cipher/result, GI/STBC/AMPDU and bandwidth fields.
  Statistics declare signed RSSI, protocol/rate, antenna SNR/RSSI and phase
  increment. Target compiler/endian layout, actual wire export, frame FCS
  retention and IV/MIC handling remain to be validated.
* ``forward/hmac_rx_data_filter.c`` consumes descriptor status, including
  FCS/MIC/key-search and replay failures. Its error handling permits some
  paths to continue, so generic status alone cannot justify a claim that
  the Host checked replay protection.
* ``hmac/hmac_11i.c:hmac_11i_update_key_to_ce`` temporarily disables replay
  detection for certain non-PTK updates and arms a timer to re-enable it.
  The conditional fragment check in ``feature/hmac_frag.c`` uses
  ``latency_index``; it does not establish a general 48-bit CCMP PN export.
  A new driver must establish key/replay ownership across rekey, reinstall,
  reordering and failure before setting mac80211 DECRYPTED, IV_STRIPPED or
  PN_VALIDATED flags. In particular, IV_STRIPPED removes the stack's ability
  to perform replay detection itself.

Reproduction and remaining gates
--------------------------------

After checking the whole machine's build/VM load, reserve a share of the
8-job budget when hardware regression is active, then run from this tree::

   python3 tools/testing/ws73/run-kunit.py --jobs 4

The runner uses a fixed sibling ``.dev/ws73-upstream/build-kunit`` directory,
a private QMP socket, and timestamped records. QEMU uses KUnit's default accelerator selection, two virtual CPUs,
no network device and no USB passthrough. KASAN and UBSAN execute the same
codec objects that a subsequent driver can link. The runner records HEAD,
dirty patch/untracked hashes, compiler/tool identities, exact command,
config, binary/object hashes, raw serial log and all named test results.
It rejects missing cases, skipped cases, source changes and absent artifacts.
No firmware/board/device claim is made for this synthetic VM run.

Still required: qualified physical-parent firmware/board/startup integration,
independent device passthrough with cold boot and runtime identity agreement,
physical USB class-control/startup qualification, complete HCI initialization,
BlueZ and peer communication. Implemented codecs, loader sequencing, bounded
H4 reassembly, BLE action engine and native HCI model coverage do not by
themselves qualify those physical paths.
The user reports no BLE peer available. PM, recovery, coexistence, multi-device,
Wi-Fi STA, fuzzing and formal qualification remain separate open gates.
